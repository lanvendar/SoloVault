# SoloVault (PWA) 设计文档修订版

## 1. 目标与边界

SoloVault (PWA 版) 是一款轻量级、可离线、跨平台的个人密码管理器，面向 macOS、Windows、iOS 和 Android 设备。目标是：

- 所有加解密仅在本地浏览器执行
- 默认无服务端、无账号体系
- 支持安装为 PWA，在主流桌面和移动平台使用
- 支持 Vault 文件导入导出
- 支持通过 `.vault` 文件在设备间迁移
- UI 简洁，便于后续 agent 直接实现

非目标：

- 不承诺抵御已获取同源脚本执行能力的攻击者
- 不实现“输错几次自动销毁数据”
- 不把浏览器本地存储包装成“永久不丢失”

设计原则：

- 安全边界说清楚，避免伪安全
- 主流程优先，异常流程少而明确
- 数据模型稳定，方便迭代
- 默认实现成本可控

---

## 2. 产品结构

应用只保留 4 个核心界面：

1. 初始化页
2. 解锁页
3. 主列表页
4. 新增/编辑弹窗

高级能力通过独立弹窗进入：

- 导出 Vault 文件
- 离线扫描导出
- 导入 Vault 文件
- 离线扫描导入
- 批量文本编辑

## 3. 核心交互

### 3.1 初始化页

当本地不存在 vault 时展示：

- `创建新密码库`
- `导入 .vault 备份`

创建新库流程：

1. 输入主密码
2. 确认主密码
3. 展示密码强度
4. 创建 vault
5. 展示恢复码
6. 用户确认已保存恢复码后进入解锁页

约束：

- 主密码至少 12 位
- 恢复码仅展示一次
- 恢复码支持复制和下载文本

### 3.2 解锁页

展示：

- 主密码输入框
- 解锁按钮
- 导入 Vault 文件入口
- 使用恢复码重建主密码入口
- 清空本地数据入口

失败策略：

- 密码错误只给出通用提示，不提示具体原因
- 使用指数退避节流，例如 1s / 2s / 4s / 8s，上限 30s
- 不做本地自毁，不做失败次数持久化防篡改

原因：

- PWA 无法可靠实现防篡改失败计数
- 自动销毁会放大误触、儿童误输、键盘布局错误等真实风险

### 3.3 主列表页

顶部工具栏：

- 锁定
- 搜索
- 新增
- 导出 Vault 文件
- 离线扫描导出
- 导入 Vault 文件
- 离线扫描导入
- 批量编辑

列表默认用扁平卡片：

- 标题
- 用户名
- 密码（默认隐藏）
- URL（可选）
- 备注摘要（可选）
- 复制用户名
- 复制密码
- 编辑
- 删除

不做折叠层级。

### 3.4 新增/编辑弹窗

字段：

- `username` 必填
- `password` 必填
- `title` 选填
- `url` 选填
- `note` 选填
- `totpSecret` 选填，作为后续能力预留

规则：

- 未填 `title` 时，优先取 URL hostname；否则显示“未命名条目”
- `url` 做基本格式校验，不强制必须带协议

### 3.5 批量编辑

不建议继续使用 Markdown 作为存储编辑协议，改为“结构化纯文本模板”。

原因：

- Markdown 自由度高，解析歧义大
- 标题、列表符号、空行数量都容易造成误解析
- 后续 agent 做导入校验和错误定位会更复杂

建议格式：

```txt
title: 微博
username: weibo_user
password: weiboPwd123
url: https://weibo.com
note: 绑定常用手机号

title: 豆瓣
username: douban_user
password: doubanPwd456
url:
note:
```

规则：

- 空行分隔条目
- 每行 `key: value`
- key 只允许 `title username password url note totpSecret`
- `username` 和 `password` 缺失时整条报错
- 保存前先预解析并展示“将新增/覆盖/报错”的结果

## 4. UI 交互与视觉设计规范

### 4.1 设计目标

SoloVault 的界面应像一个可靠的本地工具，而不是营销网站。

关键词：

- 安静
- 清晰
- 高信任感
- 移动端优先
- 操作路径短
- 危险操作明确隔离

视觉上避免：

- 大面积渐变背景
- 装饰性卡片堆叠
- 过度圆角
- 大 hero 标题
- 过多解释性文案

### 4.2 全局布局

页面结构：

```txt
AppShell
  Header
  Main
  ToastLayer
  ModalLayer
```

桌面端：

- 内容最大宽度：960px
- 主体居中
- 左右留白 24px
- 列表卡片单列展示

移动端：

- 内容宽度占满
- 左右留白 16px
- 顶部工具栏允许换行
- 关键按钮不小于 44px 高

整体背景：

- 页面背景使用接近白色或极浅灰
- 主内容不放进大卡片
- 只给条目、弹窗、危险确认使用卡片容器

### 4.3 色彩与层级

建议色彩：

- 背景：`#F7F8FA`
- 表面：`#FFFFFF`
- 主文本：`#111827`
- 次文本：`#6B7280`
- 边框：`#E5E7EB`
- 主操作：`#2563EB`
- 成功：`#059669`
- 警告：`#D97706`
- 危险：`#DC2626`

规则：

- 主色只用于主要按钮、焦点态、选中态
- 危险色只用于删除、清空本地数据等高风险操作
- 不使用单一蓝紫渐变铺满页面
- 所有文字和背景对比度要满足日常移动端可读性

### 4.4 字体与间距

字体：

- 系统默认 sans-serif
- 不使用花体或品牌字体
- 标题 20-24px
- 区块标题 16-18px
- 正文 14-16px
- 辅助说明 12-13px

间距：

- 页面区块间距 24px
- 表单字段间距 12px
- 卡片内边距 16px
- 弹窗内边距 20px
- 按钮间距 8px

圆角：

- 输入框、按钮、卡片统一 8px
- 不使用超大胶囊风格，除非是小型状态标签

### 4.5 按钮与图标

按钮类型：

- Primary：创建、解锁、保存、导入确认
- Secondary：导出、离线扫描、取消
- Ghost：锁定、复制、显示密码、编辑
- Danger：删除、清空本地数据

图标建议：

- 锁定：lock
- 搜索：search
- 新增：plus
- 导出 Vault 文件：download
- 导入 Vault 文件：upload
- 离线扫描导出：qr-code
- 离线扫描导入：scan-line
- 复制：copy
- 显示/隐藏密码：eye / eye-off
- 编辑：pencil
- 删除：trash

规则：

- 工具栏按钮优先使用图标 + 简短文字
- 卡片内高频操作可用图标按钮
- 图标按钮必须有 tooltip 或 `aria-label`

### 4.6 初始化页

布局：

```txt
[SoloVault]
[本地离线密码库]

[创建新密码库]
[导入 Vault 文件]
```

创建表单展开在当前页，不跳转：

- 主密码
- 确认主密码
- 密码强度条
- 创建按钮

恢复码展示：

- 使用等宽字体
- 按组分隔
- 提供 `复制恢复码`
- 提供 `下载恢复码`
- 勾选确认后才允许继续

交互：

- 主密码不一致时实时提示
- 密码强度弱时允许继续，但要提示风险
- 创建期间按钮进入 loading，文案为“正在创建”

### 4.7 解锁页

布局：

```txt
[SoloVault]
[密码库已锁定]

[主密码输入框] [显示/隐藏]
[解锁]

[导入 Vault 文件] [使用恢复码重设主密码]

[清空本地数据]
```

交互：

- 回车触发解锁
- 解锁失败输入框轻微震动
- 节流期间按钮禁用并显示倒计时
- 清空本地数据放在底部危险区

危险区：

- 默认弱化显示
- 点击后弹确认弹窗
- 必须输入 `WIPE` 才能确认

### 4.8 主列表页

顶部工具栏：

```txt
[锁定] [搜索输入] [新增]
[导出 Vault 文件] [离线扫描导出] [导入 Vault 文件] [离线扫描导入] [批量编辑]
```

桌面端：

- 第一行放锁定、搜索、新增
- 第二行放导入导出和批量编辑
- 搜索输入占据剩余宽度

移动端：

- 搜索独占一行
- 其他按钮使用两列网格或横向滚动工具条
- 不让按钮文字挤压换行到不可读

空状态：

```txt
暂无条目
[新增条目]
[导入 Vault 文件]
```

搜索无结果：

```txt
没有匹配结果
[清空搜索]
```

### 4.9 条目卡片

卡片内容：


规则：

- 不做折叠展开
- 密码默认隐藏
- URL 长文本单行省略
- 备注只展示一行摘要
- 复制成功显示 toast
- 删除使用确认弹窗，不用浏览器原生 confirm

卡片状态：

- hover：边框略微加深
- focus-within：显示主色描边
- 删除中：按钮 disabled，显示 loading

### 4.10 新增/编辑弹窗

弹窗字段顺序：

1. 标题
2. 用户名
3. 密码
4. 网址
5. 备注

按钮：

- 主按钮：保存
- 次按钮：取消

交互：

- 用户名和密码为空时禁用保存或保存时定位错误
- 密码字段带显示/隐藏按钮
- 后续密码生成器入口放在密码字段右侧
- 保存成功关闭弹窗并显示 toast

结构：

```txt

```

交互：

- 打开时自动填入当前条目文本

- 有错误时禁用“保存覆盖”

文本编辑区：

- 使用等宽字体

- 移动端高度不超过视口 50%

导出 Vault 文件：

- 点击后直接生成并下载 `.vault`
- 成功后 toast：`Vault 文件已导出`
- 失败时保留在当前页面并显示错误

导入 Vault 文件：

- 使用系统文件选择器
- 只接受 `.vault`，但仍要做内容校验
- 本地已有 vault 时弹出覆盖确认
- 导入成功后跳转解锁页

覆盖确认文案：

```txt
导入后会替换当前本地密码库。请确认你已经导出过当前数据。
```

交互：

## 5. 密码学设计

### 5.1 推荐方案

- KDF: `Argon2id` 优先；若浏览器兼容或包体受限，降级到 `PBKDF2-HMAC-SHA256`
- 内容加密: `AES-256-GCM`
- 随机数: `crypto.getRandomValues`

实现建议：

- KDF 运行在 Web Worker
- 参数可写入 vault header，便于未来迁移

### 5.2 密钥结构

只保留一把数据密钥 `DEK`：

1. 随机生成 256-bit `DEK`
2. 使用主密码派生出的 `KEK_pw` 加密 `DEK`
3. 使用恢复码派生出的 `KEK_rec` 加密同一个 `DEK`
4. 使用 `DEK` 加密整个条目数据

说明：

- 不额外引入自定义 HMAC 层
- `AES-GCM` 已提供完整性校验
- 只要版本化 header 设计清晰，后续可平滑升级参数

### 5.3 KDF 参数

建议：

- `Argon2id`: 以设备性能压测结果为准，目标解锁耗时 300ms-1200ms
- `PBKDF2-HMAC-SHA256`: 默认 600,000 次可作为初版起点，但要允许配置迁移
- 恢复码轨道不要明显弱于主密码轨道，避免成为旁路短板

恢复码建议：

- 长度改成至少 128-bit 熵，不再写“64 位恢复密钥”
- 展示为分组字符串，例如 8 组 4 字符

## 6. 数据模型

### 6.1 Vault 文件结构

```json
{
  "version": 1,
  "kdf": {
    "algorithm": "argon2id",
    "params": {
      "memoryKiB": 65536,
      "iterations": 3,
      "parallelism": 1
    },
    "saltPw": "...",
    "saltRec": "..."
  },
  "envelope": {
    "dekByPassword": {
      "iv": "...",
      "ciphertext": "..."
    },
    "dekByRecovery": {
      "iv": "...",
      "ciphertext": "..."
    }
  },
  "payload": {
    "iv": "...",
    "ciphertext": "..."
  },
  "meta": {
    "createdAt": 1700000000000,
    "updatedAt": 1700000000000
  }
}
```

### 6.2 解密后数据结构

```json
{
  "entries": [
    {
      "id": "uuid",
      "title": "微博",
      "username": "weibo_user",
      "password": "weiboPassword123",
      "url": "https://weibo.com",
      "note": "个人辅助备注说明",
      "totpSecret": null,
      "createdAt": 1700000000000,
      "updatedAt": 1700000000000
    }
  ]
}
```

约束：

- 统一使用 camelCase
- 不预埋无实际使用的字段
- `totpSecret` 可选，但 UI 初版可以隐藏

## 7. 本地存储与写入

### 7.1 存储介质

- 主存储：IndexedDB
- 会话态：内存
- 非敏感 UI 配置：LocalStorage 可选

### 7.2 写入策略

初版不必实现 WAL 风格多键事务模拟，直接使用 IndexedDB 单记录覆盖写入：

1. 生成完整新 vault blob
2. 写入 `vault.current`
3. 成功后更新内存态

如果需要增强可靠性，再加：

- `vault.backup`
- 写前备份
- 启动时恢复

理由：

- 单 vault 文件模型已经足够简单
- 自定义 tmp + hmac 流程实现成本偏高，收益有限

## 8. Vault 导入导出

产品只保留两种数据转移方式：

1. Vault 文件导入导出：主路径
2. 离线扫描导出 / 离线扫描导入：辅助路径

两者都不是“同步”。

原因：

- `.vault` 文件已经是完整加密后的可迁移载体
- 文件迁移更容易实现、验证和恢复
- 离线扫描适合无法方便传文件的纯离线场景
- “同步”会让用户误以为存在冲突合并和自动更新

### 8.1 导出 Vault 文件

导出流程：

1. 用户点击 `导出 Vault 文件`
2. 应用生成当前最新的 `VaultFile`
3. 下载文件名建议为 `solovault-backup-YYYYMMDD-HHmm.vault`
4. UI 展示备份时间与短校验摘要

### 8.2 导入 Vault 文件

导入流程：

1. 用户点击 `导入 Vault 文件`
2. 用户选择 `.vault` 文件
3. 应用解析并校验文件结构
4. 如果本地已有 vault，提示“覆盖当前库”
5. 用户确认后写入 IndexedDB
6. 跳转到解锁页，由用户输入主密码验证

约束：

- `.vault` 文件内容就是完整 `VaultFile`
- 导入前必须做 schema 校验
- 导入不要求立即解密，但导入后必须回到解锁页
- 覆盖本地 vault 前必须二次确认

### 8.3 离线扫描导出

定位：

- 这是离线场景下的导出方式，不是同步
- 输出仍然是完整加密后的 vault 数据
- 展示方式是 QR 分片，适合无法传输文件的设备间备份

流程：

1. 用户点击 `离线扫描导出`
2. 应用读取当前完整 `VaultFile`
3. 序列化后按容量切成多个 QR 分片
4. 展示当前分片、总分片数、整体校验摘要短码
5. 用户用另一台设备执行 `离线扫描导入`

### 8.4 离线扫描导入

流程：

1. 用户点击 `离线扫描导入`
2. 扫描分片
3. 在内存中按序组装
4. 校验完整 payload hash
5. 解析为 `VaultFile`
6. 提示“导入为当前本地库”
7. 导入后回到解锁页验证

约束：

- QR 承载的是完整加密后的 vault blob 分片
- 所有分片共享同一个 `payloadHash`
- 完整组装后才允许导入
- 组装成功后走与 `导入 Vault 文件` 相同的 schema 校验和覆盖确认流程
- 不做增量同步
- 不做冲突合并
- 不在 QR 层额外发明加密协议

分片结构建议：

```json
{
  "sessionId": "uuid",
  "index": 1,
  "total": 5,
  "chunk": "...",
  "chunkHash": "...",
  "payloadHash": "..."
}
```

## 9. 剪贴板与内存安全

### 9.1 剪贴板

支持“30 秒后尝试清空剪贴板”，但必须写清限制：

- 浏览器未必有权限覆盖系统剪贴板
- 用户可能在倒计时期间复制了别的内容
- 因此只能作为 best effort，不可承诺

UI 建议：

- 复制成功 toast
- 显示“30 秒后尝试清空”
- 提供“立即清空”按钮

### 9.2 内存清理

可以对 `Uint8Array` 等缓冲区做覆盖清零，但不能把这项能力表述为强保证。

要求：

- 锁定时清空内存态
- 页面隐藏超过阈值可自动锁定
- Worker 完成 KDF 后尽快释放中间 buffer

## 10. PWA 约束

可实现项：

- 安装到主屏幕
- Service Worker 缓存静态资源
- 离线打开应用

不要承诺：

- 浏览器永不清理本地数据
- `navigator.storage.persist()` 一定成功
- 所有平台拥有一致生命周期

产品文案建议：

- “建议导出备份”
- “建议安装为 PWA”
- “浏览器清缓存或系统回收空间可能导致本地数据丢失”

## 12. 给后续 Agent 的实现约束

### 12.1 前端状态

- 解锁前不加载明文 vault 到全局状态
- 解锁后明文数据仅保存在内存 store
- 锁定时销毁内存 store

### 12.2 模块拆分

- `crypto/`: KDF、加解密、编码转换
- `storage/`: IndexedDB 读写
- `vault/`: schema、导入导出、版本迁移
- `features/entries/`: 列表与编辑
- `features/import-export/`: `.vault` 文件导入导出
- `features/offline-scan/`: 离线扫描导出 / 导入

### 12.3 错误处理

- 导入错误要区分：格式错误、版本不支持、密码错误、完整性校验失败
- 批量编辑错误要定位到条目序号和字段名
- 所有危险操作二次确认

## 13. 最终结论

这个产品方向成立，但原文档里“自毁、防篡改、永久存储、Markdown 解析、设备同步”几个点存在明显过度设计或错误安全预期。

修订后建议采用：

- 简单稳定的加密信封模型
- 明确的浏览器安全边界
- 可解释的失败节流，而不是销毁数据
- 可维护的结构化文本导入
- 以 `导出 Vault 文件` / `导入 Vault 文件` 为主，`离线扫描导出` / `离线扫描导入` 为辅

这版更适合作为后续 agent 的实现输入。
